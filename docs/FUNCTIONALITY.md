# Toogether — Functionality Documentation

**This is the canonical, living reference for what the app actually does.** Update it in the same change as any feature work — new screen, changed flow, gate added/removed. If this doc and the code disagree, the code wins; fix the doc.

Its companion doc is [`DATABASE.md`](./DATABASE.md) (schema/RLS/migrations, not feature behavior). Together these two are the only living docs for this project — old topic docs have been retired, see the note at the bottom.

> This doc distinguishes **real** (backed by Supabase, verified in the current code) from **local-only / mock** (React state that resets on logout, never persisted) wherever it matters — that distinction has bitten this project before (see the retired `CURRENT_FUNCTIONALITY_STATUS.md`, which went stale within two weeks because it didn't separate the two clearly and wasn't kept current).

## 0. Product concept

Toogether is a spontaneous social planning app: discover nearby real-world plans, request to join safely, meet people through shared activities, and turn good interactions into a trusted crew. Three core loops: **discover** (browse the feed), **join/host** (request to join or create a plan), **build trust** (ratings, crew connections, verification).

Safety/trust model by design: a plan's locality + time-of-day are public, but its exact address/time is only revealed to approved joiners (app-level, not RLS-enforced — see `DATABASE.md` §3.2); hosts approve who joins; women-only plans are filterable; verification (§7), crew connections (§4, real since 2026-10-11) and ratings (§4, still mock) are meant to build a reputation layer over time. Eight plan categories: movies, chill, music, sports, food, travel, gaming, other.

## 3. Auth & onboarding

`providers/auth-provider.tsx` owns session state:
1. On mount, it first decodes whatever session is already on disk via `getStoredSessionClaims()` (`utils/supabase.ts`) — a pure local read of the persisted JWT, no network call — and renders the app as logged-in immediately if one is found. This "optimistic local-first" step exists because the naive alternative (wait for `supabase.auth.getClaims()`/`getSession()` before deciding) bounced returning users to `/auth` whenever a cold start raced a slow network (very common in a standalone/preview build; rare enough in dev to go unnoticed) — the SDK call would time out, and a timeout was being treated identically to "no session."
   - `isLoading` (exposed as `isAuthLoading`, and folded into `AppProvider`'s `isAppReady`) is only cleared once the profile fetch for those claims actually resolves — not the instant claims are known. `AppProvider.currentUser` is derived from `profile`, not `claims`, so clearing `isLoading` any earlier left a one-frame window on every cold start where `isAppReady` was `true` but `currentUser` was still `null`; `app/index.tsx` read that as "ready, and logged out" and redirected to `/auth` even though the stored session was perfectly valid (fixed 2026-08-25 — this was the "swipe app from recents, reopen, bounced to /auth" bug). `fetchProfile()` also now retries with backoff (like `verifyClaims()` below) instead of nulling the profile out on a first-fetch network hiccup with no prior profile to fall back on, and `app/auth.tsx`'s `currentUser` watcher now silently redirects home if this screen is ever reached while already logged in (previously only self-healed mid-login-attempt), as a second line of defense against any future variant of this race.
   - Separately, `fetchProfile()` used to call `setIsLoading(true)` at the start of every call, not just the first one — but `claims` gets a brand-new object reference on every `onAuthStateChange` event, including a routine background `TOKEN_REFRESHED` that `autoRefreshToken` fires periodically for the *same already-logged-in user*. Each of those re-triggered the `[claims]` effect → `fetchProfile()` → `isLoading` flipping true again, which flipped `isAppReady` back to `false` well after startup — visibly resetting the whole app back to its splash screen during completely normal, idle use, including right after toggling system theme (a plausible AppState-adjacent moment for a refresh to land). Fixed 2026-08-26 with a `hasLoadedOnceRef`: only the very first resolution of auth state is allowed to set `isLoading`; every fetch after that updates `profile`/`claims` silently in the background. This, not Expo Go or the OS, was the actual cause of the app appearing to "close and reopen" on a theme change.
2. It then verifies/refreshes with the server in the background (`getClaims()` → `getSession()` fallback, with backoff retries). Only a confirmed server-side rejection (`isAuthApiError`/`isAuthSessionMissingError`) clears the session and forces `/auth` — a network/timeout failure (`AuthRetryableFetchError`) or any other inconclusive error just retries and otherwise leaves the optimistic claims alone.
3. `onAuthStateChange`'s `SIGNED_OUT` event is treated the same way unless it followed an explicit call to `logout()` (tracked via `markExplicitSignOut()`) — an un-flagged `SIGNED_OUT` re-verifies with the server rather than being trusted outright, since supabase-js is known to fire that same event on its own failed-refresh session wipe (see the comment in `utils/supabase.ts`), not just on a real sign-out.
4. Once claims exist, `fetchProfile()` selects the `profiles` row for `id = claims.sub`.
5. **If no row exists** (`PGRST116`), it auto-creates one: default name from the email's local-part, a generated `username`, empty `city`, a random avatar color pair. This is the entire "create profile" step — there's no separate explicit insert racing it.
6. Separately from the JS-state churn in point 1 above, Android can kill and later recreate the app's process for reasons that have nothing to do with any bug here — e.g. backgrounding it while its own Quick Settings panel is open to flip the system light/dark theme, on a device under memory pressure. `android:configChanges` already includes `uiMode` (Expo's default template), so a same-process theme flip alone does *not* trigger this; it's specifically the process being backgrounded and reclaimed that does. Either way, the whole JS engine — including expo-router's in-memory navigation stack — starts fresh at `app/index.tsx`, and a hardcoded `<Redirect href="/(tabs)/home">` there made every such relaunch look like "the app reset itself and lost my place," even on a screen several levels deep. Fixed by having `AppProvider` persist the current pathname (`RouteTracker` in `app/_layout.tsx`, via `usePathname()`) to AsyncStorage as `lastRoute` on every navigation while a user is logged in, skipping pre-auth screens and one-off modals (`create-event`, `location-picker`, `paywall`) whose form state wouldn't survive anyway. `app/index.tsx` redirects there instead of always to Home; `logout()` clears it so a fresh login doesn't resume into a leftover route from a previous session.

   **Restore is limited to system-initiated relaunches** (changed 2026-09-15). The original version restored on *every* cold start, so swiping the app out of recents and reopening it also resumed deep inside (e.g. on Settings) instead of starting on Home. The rule now:

   - **Swiped out of recents, or first launch:** Home.
   - **Still in recents with its process alive:** Android/iOS resume the running app natively. No JS involved.
   - **Still in recents but the system reclaimed the process:** back on the last screen.

   JS cannot tell the last two cold-start cases apart, because both are a fresh process with no memory of how the previous one died. The native signal is whether Android recreates the activity from saved instance state: Android keeps that state with the task in recents and discards it when the task is swiped away. The generated `MainActivity` passes `null` to `super.onCreate` (Expo template), which also hides the value from Expo's `ReactActivityLifecycleListener`s. So `modules/launch-state` (a local Expo module, Android-only, autolinked from `modules/`) reads it through the public `Application.ActivityLifecycleCallbacks.onActivityPreCreated` (API 29+). `Activity.performCreate` dispatches that callback with the bundle the system delivered, before `onCreate` runs. It records the value for the process's first activity and exposes it to JS as `wasRestoredBySystem()`. `AppProvider` only uses the stored `lastRoute` when that returns true. Uses no reflection, private APIs, permissions, or patching of generated native files.

   **Limits:** falls back to Home on every cold start where the native signal isn't available — iOS (no equivalent wired up; its native resume-while-alive still works), Expo Go, web, and Android 9 and below. Native change: needs a new dev/EAS build, a JS reload won't pick it up.

Session persistence itself (`utils/supabase.ts`) stores only a small random AES key in `expo-secure-store` (well under its ~2048-byte Keychain/Keystore limit) and keeps the actual session — encrypted with that key — in `AsyncStorage`, which has no practical size limit. This replaced an earlier scheme that split the session across several chunked SecureStore keys, which wasn't crash-safe: an app kill mid-write (plausible right after a fresh login) could leave an incomplete chunk set that silently read back as "no session," forcing a re-login. A one-time migration in `getItem` reassembles and re-saves any leftover chunked value from that older format.

`AppProvider.signup()`/`login()` just call `supabase.auth.signUp`/`signInWithPassword` (wrapped with a 15s timeout) — profile creation is entirely driven by the auth-state-change event above, not by the signup call itself.

`app/new-user-profile.tsx` is the real "fill in your details" step a fresh signup lands on next (the auto-created row is bare — name/city/etc. are placeholders until this screen runs). Age/DOB is validated 18+ client-side; avatar upload goes through Cloudinary.

`app/(tabs)/profile.tsx` gates on `isAppReady` before checking `currentUser` (fixed 2026-08-25) — it used to redirect straight to `/auth` on `!currentUser` with no readiness check, unlike every other `currentUser`-gated screen in the app (which just render `null` while loading). Nothing in this app persists or restores a prior navigation route across a cold start — a fresh launch always resolves through `index.tsx` first (confirmed: no `linking`/state-persistence config, no stored "last route" key) — so this specific screen shouldn't normally be the first thing mounted. But it was still a real, independent bug on its own terms: it was the only auth-gated screen that force-navigated instead of waiting, which made it a second latent path to the same "bounced to /auth while still logged in" symptom fixed in §3, reachable by anything that might mount it before auth resolves (present or future — e.g. a deep link added later).

`socialAuth()` (Google/Apple) is a `console.log` stub — not implemented.

## 4. Events, requests, messaging, ratings, crew — what's real vs. local-only

All of this lives in `providers/AppProvider.tsx`.

### Real (backed by Supabase)

- **Create** (`createEvent`): checks the create-limit gate (§5), inserts into `events`, optimistic local update. Throws `'Plan creation limit reached'` if gated — caught by `create-event.tsx`, which routes to `/paywall`. The date picker (`create-event.tsx`) caps how far out an event can be scheduled at **1 month** (2026-10-11, was 2 years): the same date next month, clamped to that month's last day (Jan 31 → Feb 28), any time that day (`maximumDate`, both the Android `DateTimePickerAndroid` and iOS inline `DateTimePicker`). Enforced server-side by `validate_event()` (migration 016). **Required fields (2026-10-11, `PLAN_LIMITS` in `lib/profileFields.ts`)**:
  - **Must be filled**: title (3–60 characters), date, time, public locality, exact address (max 200), and **group size** (2–10, including the host). Group size used to be optional, and blank meant unlimited.
  - **Start time**: at least 15 minutes from now. The date picker only blocked past *days*, so an earlier time today used to post a plan that had already started. That happened in production on 2026-10-10: several plans were created with a start time equal to their creation time, and Home hid them as already started, so to their hosts they "showed in my plans but not on Home". The time picker also used to open on the current time, so accepting its default produced exactly that. It now opens on the next half hour at least an hour away (`getSuggestedStartTime()`).
  - **Optional**: description (max 200) and location note (max 90), both with counters.
  - **Cleaning**: whitespace is collapsed before saving, so a spaces-only title or address counts as empty.
  - **Feedback**: the Drop the Plan button stays disabled while anything is missing, with a "Still needed: …" line above it. Everything is re-checked on tap, since the clock moves while the form is open.
  - **Server-side**: the `validate_event()` trigger (migration 015, `DATABASE.md` §3.2) enforces the same rules for any client. The Edit plan sheet uses the same description length limit.
- **Lifetime / archiving (2026-10-11, migration 016)**. Nothing is ever deleted automatically:
  - **Before the start**: public; shows on Home.
  - **From the start to +6h**: off the public feed (`hasEventStarted`), but in Home's **Happening now** section for the host and members, and still under Profile → Hosting / Joined, marked "Happening now · chat closes …". The details page and chat work as normal.
  - **From +6h (archived, `isEventArchived()` / `archivesAt()` in `lib/eventTime.ts`)**: everyone except the host and approved members loses the plan entirely. For the host and members it's a **list entry only** in Profile → Past plans, which since 2026-10-11 holds only closed plans, newest first: a row with a lock icon, not tappable, showing "Hosted"/"Joined", the date and the area. `app/event/[id].tsx` and `app/chat/[id].tsx` show `components/PlanClosedScreen.tsx` instead of details or chat, including when opened from an old notification. They also show it, without plan details, when the plan isn't visible at all, which replaced the bare "Event not found". The database enforces all of this, not just the UI; the chat closes for reads and new messages.
  - **Admins** (the separate `together-admin` panel, signed in as an `admin_users` member) keep everything: plan, requests and chat, through the `is_admin()` clauses.
  - **A cancelled plan** is hidden from everyone immediately and stays admin-visible.
  - **Actually removing rows** is a manual admin purge, and now only for cancelled plans: archived plans are the members' history. See `DATABASE.md` §3.2.
- **Feed/browse**: `syncEventsAndRequests()` fetches all `events` + `join_requests`. State keeps raw event rows and raw requests separately, and each event's `approvedUserIds`/`requestUserIds` is *derived* from `requests` (`useMemo` → `hydrateEvents`). Mutations only touch `requests`, so the two can't drift. Plain `useEffect`/`useState`, no pagination, no React Query (`hooks/useFeed.ts` is unused). Which `events` rows come back is governed by RLS, not a client-side filter — see the soft-delete/retention note below. The data stays fresh three ways (added 2026-10-02):
  - **Realtime**: the `feed-realtime` channel streams `join_requests` and `events` INSERT/UPDATE/DELETE into state, upserting by id so a local optimistic write and its realtime echo never duplicate. Needs migration 012.
  - **Resume resync**: every background → foreground transition (throttled to once per 5s) re-runs `syncEventsAndRequests()`. Realtime can't deliver while the app is backgrounded, which is exactly when a "wants to join" push arrives. Before this, tapping that push opened the event with a stale request list, and the request only appeared after a manual pull-to-refresh.
  - **Unknown profiles**: the full `profiles` list is only fetched at login, and the event screen skips request rows it can't resolve to a user. So `ensureUsers()` fetches any requester or creator profile that isn't loaded yet (e.g. someone who signed up after you logged in).
  - `app/event/[id].tsx` shows a skeleton rather than "Event not found" while a sync is in flight, for when it's opened straight from a push.
- **Join request** (`requestToJoin`): blocks women-only events for non-women, full events, and events whose `dateTime` has already passed ("This plan has already happened.") — mirrored server-side by the `join_requests_insert_own` RLS check (`DATABASE.md` §3.3). Also checks the join-limit gate (§5), inserts into `join_requests` with a client-side double-tap guard and a `23505` unique-violation recovery path (re-syncs from DB instead of surfacing an error).
- **Delete** (`deleteEvent`, called from `app/event/[id].tsx`'s "cancel plan" flow): soft delete, not a hard `DELETE` — sets `events.deleted_at`, same optimistic local removal as before so the UI looks identical to a hard delete. The row stays in the DB, invisible to every non-admin user immediately, and admin-queryable for a retention window before a human purges it manually (no automated purge job). Same retention treatment applies to an event that simply completes (its `date_time` passing) rather than being explicitly deleted — full timing model, exact windows, and the manual purge query are in `DATABASE.md` §3.2.
- **Approve/reject** (`approveRequest`/`rejectRequest`): updates `join_requests.status` + the local request (the event's attendee lists follow automatically).
- **Request again after a decline** (`rerequestToJoin`, 2026-10-10): a declined requester gets 2 more tries, 3 requests in total (`MAX_JOIN_REQUEST_ATTEMPTS` in `lib/types.ts`). It reuses the same row (`rejected` → `pending`) through the `rerequest_to_join()` RPC, which enforces the limit and the plan-hasn't-started check server-side. `join_requests.attempts` counts the sends. It counts toward the join-request usage gate like a first request. The host gets an "X asked again to join Y" notification.
- **Remove a member** (`removeMember`, 2026-10-10): host only. Sets the member's request to `removed`, a final status: they drop out of the attendee list, lose chat and private details (RLS only admits `approved`), can't re-request that plan, and get a "You were removed from …" notification. See `DATABASE.md` §3.3.
- **Invite** (`inviteToEvent` / `respondToInvite`, reworked 2026-10-11): host only, and only for accepted crew members. The `invite_to_event()` RPC checks host, crew, not started, not full and women-only, then creates an `invited` row (or turns an earlier declined/removed request into one). That status grants nothing: no attendee-list entry, chat or private details. The invitee answers with `respond_to_invite()`: accept makes the row `approved`, decline deletes it. The host gets "X is joining Y" or "X can't make Y". This used to insert an auto-approved row for the other person directly, which RLS refused (`join_requests_insert_own` only allows your own row) and which would have added people to plans without asking them.
- **Crew** (`sendCrewRequest`, `acceptCrewRequest`, `rejectCrewRequest`, `getCrewStatus`, `getCrewMembers`; real since 2026-10-11): `crewRequests` holds the real `crew_requests` rows you're on either side of. It's fetched at login and on resume and kept live through the `feed-realtime` channel, and it's cleared on logout. Every write goes through an RPC (`DATABASE.md` §3.5): `send_crew_request()` (if they had already asked you, this accepts their request; an old declined request is cleared so either side can ask again), `respond_to_crew_request()`, and `remove_from_crew()` (`removeFromCrew`, 2026-10-11). Removing ends the connection, or cancels a pending request from either side, and withdraws unanswered invites between the two of you; plans either of you already joined are untouched, and the other person isn't notified. It's offered by tapping "In your crew" or "Crew request sent" on their profile (with a confirmation), and as **Remove** on crew cards in the People tab (only for real crew, not people you've just shared plans with). The other person gets an Activity notification and push: "X wants to add you to their crew", which opens X's profile with an Accept button, or "X is now in your crew". `getCrewStatus` treats a declined request as no relationship. Before this, crew was an in-memory list seeded with two fake users that never left the phone, so two real people could never connect.
- **Chat** (`sendMessage`, `refreshEventMessages`): inserts into `messages`; a global Supabase Realtime channel (`messages-realtime`, `postgres_changes` INSERT) pushes new messages into local state live for anyone subscribed; `refreshEventMessages` re-fetches a specific event's messages when its chat screen opens (access can change after the login-time snapshot).

### Local-only / mock (React state, resets on logout — despite real tables existing for these in the DB, see `DATABASE.md` §3.5)

- **Ratings** (`rateUser`, `getUserAverageRating`, `getMyRatingForUser`): plain `useState`, seeded from `MOCK_RATINGS` in `lib/mockData.ts`. **Never written to the `ratings` table.** A person's rating is the plain average of stars they've received (no weighting). **Shown as "Rating", color-coded (2026-10-11; was called "Karma")**: `lib/rating.ts` bands it 4.0+ green, 3.0–3.9 yellow, below 3.0 red (theme `status.success/warning/danger`), and "New" in muted when unrated. `components/RatingBadge.tsx` (star + value pill) is used on event cards, the plan page host row, People rows and the other-user Trust snapshot; the Profile tab and other-user stat tiles color the value text the same way.
Crew connections used to be listed here; they're real now (above).

If you're building anything that assumes ratings persist across sessions or are visible to a backend/admin tool, they currently don't — this would need a real Supabase-backed implementation first.

## 5. Credits / monetisation

**Is there a limit on how many plans someone can create? Not in practice (as of 2026-10-11).** `FREE_CREATE_LIMIT = 3` per month exists, but only applies when monetisation is on. `APP_VERSION = 'free'` in `lib/monetisation.ts`, so the default mode is `free` and the gate is off. Even when on, the count is in-memory, resets on logout or reinstall, and isn't checked server-side. There's also no cap on how many upcoming plans one person can have open at once.

`lib/monetisation.ts` + gating calls inside `providers/AppProvider.tsx`. Entirely client-side — no payment provider integration.

- `FREE_JOIN_LIMIT = 5` free join requests/month; `VERIFIED_JOIN_BONUS = 5` extra for `verified` users; `FREE_CREATE_LIMIT = 3` free event creations/month.
- Three credit packs: Starter (₹19 / 3 credits), Regular (₹49 / 10), Power (₹99 / 25). `buyCreditPack()` grants credits **instantly on tap** — no real payment happens.
- Gates: join-request limit, event-creation limit, attendee-list unlock (costs a credit to view an event's full attendee list).
- `usageState` is plain React state — wiped on logout/reinstall. **No monthly reset logic** despite the "ThisMonth" naming in field names. **No server-side enforcement** — RLS only checks row ownership, never usage counts, so nothing stops a determined client from bypassing these limits.
- Dev-only app-mode switcher (`devAppMode`: `free`/`paid`/`limit-hit`/`new-user`) lets testers preview each gated state — see §6.

Treat this whole system as a **UI-level preview of the monetisation model**, not production billing. A real launch needs a payment provider (Razorpay/Stripe), server-side credit balance + usage tracking (a `credits`/`usage` table with RLS, or an Edge Function), and monthly-reset logic that isn't just naming.

## 7. Profile verification

Full route group `app/verification/` (`index`, `documents`, `capture`, under `_layout.tsx`), preceded by the onboarding upsell `app/new-user-verification.tsx`.

**Flow**: `documents.tsx` lists the three photos; each Add/Retake opens `capture.tsx?doc=front|back|selfie`, and once all three are in, the same screen becomes review & submit. All three captures use the same shared `components/verification/PhotoCaptureScreen.tsx` (a plain "Take Photo" button → `expo-image-picker`'s `launchCameraAsync` → preview/retake/confirm), parameterized by step copy and front/back camera. Captured photos live in `store/verificationDraftStore.ts` (local-only, cleared on submit/exit) until submit.

**No automated liveness/anti-spoofing check**: earlier versions of `liveness.tsx` did real-time frame-by-frame face tracking (`react-native-vision-camera` + `react-native-vision-camera-face-detector`, guided center/blink/turn-left/turn-right steps) to prove a live person was present, not a photo of a photo. That was dropped (2026-08-16) in favor of a single plain selfie capture via `expo-image-picker`, after the vision-camera dependency repeatedly caused native build/crash problems (Nitro Fabric flag breaking `react-native-maps`, MLKit's minSdk 26 requirement, etc. — see memory `camera_crash_android_rawpropsjsivalue` for the full history). Current selfie step has no more anti-spoofing property than the Aadhaar photo steps — it's just a camera-captured image. If liveness/anti-spoofing is needed again later, it needs to be reintroduced deliberately (e.g. a hosted liveness-check API) rather than a bespoke on-device frame processor.

**Submit** (`providers/AppProvider.tsx`, `submitVerification`): uploads the 3 photos to Cloudinary, then does two writes — an upsert into `verification_documents` (owner-only RLS) and an update of `profiles.verification_status='pending'` (see `DATABASE.md` §3.1, §3.6). **In that order, awaited (fixed 2026-10-10).** It used to flip to `pending` first and upload in the background. When an upload failed it quietly reset the user to `unverified` after they had left the screen. To them it looked like a successful submit that later bounced back to "Get Verified" and asked for the photos again, while an admin could see `pending` with no documents behind it. Now `documents.tsx` shows "Uploading photos (n/3)…", and a failure shows the actual error in an alert, keeps the photos in the draft store so a retry doesn't need retakes, and leaves the status unchanged. `pending` only ever appears once the documents row exists.

**Review/decide** — two paths:
- **Real admin path**: `review_verification(target_user_id, decision, rejection_reason)` RPC (`DATABASE.md` §4) — gated by `is_admin()`, snapshots the decision into `verification_reviews`, keeps `verified` in sync with `verification_status`. Call via `supabase.rpc('review_verification', {...})` using the admin's own logged-in session — no service-role key needed.
- **Dev-only self-test path**: `setVerificationStatusDev()` in `AppProvider.tsx`, gated behind `DEV_TOOLS_ENABLED`, lets a user flip their **own** status for local testing. Not usable as real moderation (RLS blocks touching another user's row outside the RPC).

**Live notification on decision (fixed 2026-08-27)**: `review_verification()` now calls `create_notification()` (`DATABASE.md` §4) as part of the same transaction that updates `profiles.verification_status`, so an approve/reject shows up in the user's Activity tab (§9) live via the `notifications` Realtime subscription — no more waiting on the next `refreshProfile()`. Out-of-app push for this (and other) notification types is not built yet — see §9's "not yet built" note.

**Known inconsistency**: `app/new-user-verification.tsx`'s "Get verified" path and the legacy quick-toggle it originally offered both ultimately funnel into the same `documents` flow today — but be aware a user could historically end up `verified=true` with `verification_status` still `unverified` if that screen's old direct-toggle behavior is ever reintroduced. Worth a quick look before trusting `verified` and `verification_status` to always agree.

**Still open, needs work outside this repo**: Cloudinary documents are still unsigned/public delivery (`DATABASE.md` §7) — needs a dashboard change + signed-URL endpoint. No data-retention/deletion policy for the raw ID photos (relevant given India's DPDP Act expectations around sensitive personal data minimization) — no delete path exists for `verification_documents` today (only `delete-avatar` exists, and only for avatars).

## 8. Building the web admin panel (for profile verification review)

No admin/web code exists anywhere in the repo yet — this is a from-scratch build. Everything it needs is already in place on the backend (`DATABASE.md` §3.6–§4):

1. **Architecture**: a Next.js (or similar) web app, Supabase Auth login (same project), no special admin login flow — "admin-ness" is just `admin_users` membership, checked server-side by RLS and by `review_verification()` itself.
2. **Bootstrap the first admin**: manual `insert into admin_users (user_id) values ('<id>')` via the Supabase SQL editor. No self-service path exists by design.
3. **Gate the UI**: call `supabase.rpc('is_admin')` after login; redirect non-admins. This is a UX nicety only — real enforcement is server-side.
4. **Screens**:
   - **Pending queue**: `select p.*, vd.* from profiles p join verification_documents vd on vd.user_id = p.id where p.verification_status = 'pending' order by p.verification_submitted_at asc` — works via the admin's own session since `verification_documents_select_own_or_admin` grants admins read access to all rows.
   - **Review detail**: render the 3 document URLs as `<img>` (still public Cloudinary URLs — the §7 caveat still applies even with DB access locked down), plus profile fields for cross-checking. Approve/Reject buttons call `review_verification()`.
   - **History** (optional): `select * from verification_reviews order by reviewed_at desc` joined to `profiles`, for "who approved this and when."
5. **The admin panel never needs the Supabase service-role key.** Keep it that way. If a future admin feature genuinely needs to bypass RLS for something `is_admin()` + a `SECURITY DEFINER` RPC can't express, follow the `delete-avatar` Edge Function template (`DATABASE.md` §6) instead of shipping the service-role key to a browser.

## 9. Notifications

**Real, Supabase-backed** — added 2026-08-27, replacing what used to be a client-computed, non-persistent "activity" list. Schema/RLS/triggers are `DATABASE.md` §3.10–§3.11, §4, §5; this section covers the app-side behavior.

**In-app inbox (built, no native rebuild needed)**: `providers/NotificationsProvider.tsx`, mounted in `app/_layout.tsx` inside `AppProvider` (so it can read `currentUser`). On login it fetches the last 100 rows of `notifications` for the current user and opens a Realtime channel (`notifications-realtime-<userId>`, filtered `user_id=eq.<id>`, mirroring the `messages-realtime` pattern) so new rows appear live without a refetch. Exposes `notifications`, `unreadCount`, `markAsRead(id)`, `markAllAsRead()`, and `dismissNotifications(ids)` / `restoreNotifications(ids)` for Activity's swipe-to-remove + Undo (soft delete via `dismissed_at`; dismissed rows are excluded from the fetch). `app/(tabs)/activity.tsx` renders `notifications` directly (title/body are pre-rendered server-side by the trigger/function that created the row — the client doesn't reconstruct copy from `type`, just picks an icon/tone/accent color per `type` via a small local lookup table); tapping a card marks it read and, if `data.route` is set, navigates there. `app/(tabs)/_layout.tsx`'s tab-bar dot is driven by `unreadCount` instead of the old locally-computed pending-join-request count, so it now reflects every notification type, not just pending joins.

**What generates a notification today** — all server-side (Postgres triggers + `review_verification()`), never inserted directly by the client (`notifications` has no client INSERT policy — see `DATABASE.md` §3.10):
- A join request is created (`join_requests` INSERT) → the event's host.
- A host invites someone (`invited` row) → the invitee (`event_invite_received`). Their answer → the host (`event_invite_accepted` / `event_invite_declined`).
- A crew request is sent → its recipient (`crew_request_received`); accepted → its sender (`crew_request_accepted`).
- A member reports another member → the host (`member_reported`). Reports about the host notify no one in the app; they're for admins.
- A join request is approved/rejected (`join_requests` UPDATE OF status) → the requester. The decline copy says whether they can still request again.
- A member is removed (status → `removed`) → that member (`join_request_removed`).
- A declined request is sent again (status → `pending`) → the host.
- A verification decision (`review_verification()` RPC) → the reviewed user.
- A new chat message (`messages` INSERT) → every other approved participant of that event (host + approved joiners, sender excluded).

**Chat messages stay out of the Activity inbox (2026-10-08)**: `new_message` rows are still created server-side, so the push webhook below still fires for chat. On the client, though, `NotificationsProvider` keeps them apart from `notifications`. It fetches only unread `new_message` rows in a separate query, so a busy chat can't push real inbox items out of the 100-row window, and Realtime inserts of that type are routed to the same list. So they never appear in `activity.tsx`, they don't count toward `unreadCount` (the Activity tab dot), and "Mark all read" doesn't touch them. Instead the provider exposes `getUnreadChatCount(eventId)`, shown WhatsApp-style through `components/UnreadBadge.tsx`. On a Home `EventCard` it appears as a "💬 N new" pill next to the Joined/Manage button that opens the chat directly; it also appears as a count badge on that plan's row in `profile-plans/[section]` and inside the Open Chat button on `event/[id]`. `app/chat/[id].tsx` calls `markChatRead(eventId)` while open, which sets `read_at` on all of that plan's unread `new_message` rows, including ones that arrive while the chat is on screen.

Crew requests are included since 2026-10-11 (trigger on `crew_requests`, `DATABASE.md` §4).

**Push notifications (built 2026-08-27, Android-only until an Apple Developer account exists)**: `expo-notifications` + `expo-device`, config plugin added to `app.json`'s `plugins` (`"expo-notifications"`, no custom options — default icon/sound, no per-platform overrides). `providers/NotificationsProvider.tsx` handles registration:

- Sets the Expo-recommended default foreground notification handler (banner + sound) at module scope, with one exception (2026-10-08): a push whose `data.route` is `/chat/<id>` for the chat currently open on screen shows no banner, list entry or sound. `app/chat/[id].tsx` sets that id through `setActiveChatEventId()` with `useFocusEffect`, so it's cleared as soon as the chat loses focus, e.g. when you open a profile from it or go back. Pushes for other chats and other types, and anything arriving while the app is backgrounded, are unaffected.
- Creates the Android `default` notification channel on mount — a platform requirement since Android 8 (API 26), not app-specific behavior.
- On login, if running on a physical device (`expo-device`'s `Device.isDevice`), requests notification permission via the stock `Notifications.requestPermissionsAsync()` (no custom pre-permission priming screen — just the native OS prompt), then calls `Notifications.getExpoPushTokenAsync({ projectId })` and upserts the result into `push_tokens` (`DATABASE.md` §3.11). `AppProvider.logout()` deletes that device's token row (`unregisterPushToken()` in `lib/pushToken.ts`) **before** calling `supabase.auth.signOut()` (fixed 2026-09-15). This used to be an effect cleanup in `NotificationsProvider`, which never removed anything, for two reasons. The query was never awaited, so it was never sent. And that cleanup only runs once `currentUser` is already null, meaning after sign-out, when the `auth.uid() = user_id` delete policy silently matches zero rows. The effect was that a logged-out device kept receiving the previous account's pushes. A session that ends without `logout()` (e.g. a failed token refresh) still leaves the row behind. In dev builds (`__DEV__`) the token is also `console.log`ged as `[push] Expo push token: ExponentPushToken[...]`, for pasting into https://expo.dev/notifications to test delivery. It is kept out of release logs because the token alone is enough to send pushes to that device.
- Tap handling via the stock `addNotificationResponseReceivedListener`, deep-linking through `data.route` — same convention the in-app list uses.
- **Deliberately no custom behavior beyond what each OS's notification APIs require**: no custom permission-priming UI, no per-notification-type toggle, no foreground suppression beyond the open-chat case above. `app/settings.tsx` has one "Notifications" row that opens system Settings via `Linking.openSettings()` when permission was denied — the standard pattern for both platforms once a permission prompt has been dismissed (neither OS lets an app re-trigger its own native prompt after a denial).

Delivery: a Database Webhook (`migrations/010_push_notifications_webhook.sql`, trigger `send_push_on_notification`) fires on every `notifications` INSERT and calls the `send-push` Edge Function (`DATABASE.md` §6), which looks up the recipient's `push_tokens` and relays through Expo's hosted push API — one call that covers both FCM v1 (Android) and APNs (iOS). Chat pushes show as **one notification per plan**, like WhatsApp (2026-10-08): each new message replaces that plan's notification with a summary of all unread messages in it, e.g. "Sunday Football (3 messages)" followed by the last 5 lines as `Rahul: hi` (details in `DATABASE.md` §6). Opening the chat calls `dismissChatPushes()` (`NotificationsProvider`) to remove that plan's notification from the tray, and marking it read means the next message starts a fresh count.

**Android needs Firebase config (added 2026-09-26)**: on Android, `getExpoPushTokenAsync()` gets an FCM token first, which needs a native Firebase app. The repo-root `google-services.json` (Firebase project `together-25cdb`, Android app `com.toogether.app`) is referenced as `expo.android.googleServicesFile` in `app.json`. It holds only client identifiers, so it's committed. Without it, registration throws `Default FirebaseApp is not initialized in this process com.toogether.app`, which is caught and logged as `Push notification registration skipped`. Delivery also needs that same project's FCM V1 service-account key uploaded to EAS (`eas credentials` → Android → Google Service Account → FCM V1). Never commit that key. The file is baked in at prebuild, so any build made before it was added has to be rebuilt.

**Why iOS doesn't work yet — and why that needs no further code**: `getExpoPushTokenAsync()` only succeeds for a platform whose push credential is configured in EAS. An APNs key requires an Apple Developer Program membership (paid), which doesn't exist for this project yet, so on iOS the call currently fails and `registerForPushNotifications()` catches it and returns quietly — no token is ever written for that platform, no crash, no visible error to the user, and the in-app inbox (§9 above) keeps working normally regardless. Once an Apple Developer account exists: run `eas credentials` to generate/upload the APNs key, ship a new iOS build via `eas build -p ios` (a native module — needs a build, not just an OTA update), and iOS devices will start registering tokens through the exact same code path Android already uses today. Nothing in this repo needs to change for that to happen.

**Not usable in Expo Go (fixed 2026-09-09) — must use a dev build**: Expo removed remote push support from Expo Go in SDK 53. `expo-notifications` isn't just non-functional there — merely `import`-ing it crashes the app on Android, because the package registers a device-push-token listener as an import-time side effect (`DevicePushTokenAutoRegistration.fx`), and that listener throws immediately when running inside Expo Go. `providers/NotificationsProvider.tsx` and `app/settings.tsx` both now `require('expo-notifications')` lazily, gated on `Constants.appOwnership !== 'expo'`, instead of a static top-level `import` — so the module is never evaluated at all when running in Expo Go, and the rest of each screen (in-app inbox, settings UI) still works there. Push registration and the permission-status row in Settings simply no-op in Expo Go. To exercise push notifications for real, use a development build (`eas build --profile development` or `expo run:android`/`expo run:ios`), not Expo Go.

## 10. Safety tips (meeting strangers in person)

Local-only, no backend involved — the tips themselves (`lib/safetyTips.ts`) and the "has the user seen this" flag are plain content + an AsyncStorage boolean, not Supabase state.

- **Content & sheet**: `lib/safetyTips.ts` exports the tip list (public places, tell someone/bring a friend, don't share personal info in chat, arrange your own transport, trust your gut); `components/SafetyTipsSheet.tsx` renders it as a bottom sheet (same `Modal`-from-bottom shape as other sheets in this app). One component, reused everywhere below rather than duplicated per screen.
- **One-time automatic nudge**: `AppProvider` exposes `shouldShowSafetyTips`/`dismissSafetyTips`, rendered globally by `SafetyTipsPrompt` in `app/_layout.tsx` (same pattern as `VerificationPrompt`, which is dead code today — never actually triggered — so don't copy its trigger side, only its render-a-global-modal shape). `AppProvider.triggerSafetyTips()` fires it exactly once, ever, per install (persisted via `AsyncStorage` key `safety_tips_seen`, guarded by a ref so two trigger calls in the same tick can't double-fire before the write lands), from whichever of these two happens first:
  - **Host**: right after `createEvent()` successfully inserts — they're about to have strangers join their plan.
  - **Joiner**: a `useEffect` in `AppProvider` watching `requests` for the current user's own `status` flipping to `'approved'` — fires regardless of which screen they're on when that happens (no per-screen wiring needed), since the request list is already global app state.
- **Persistent, always-reachable placements** (no "seen" gating — tapping these opens the same sheet unconditionally, every time):
  - `app/event/[id].tsx` — a small "Meeting up safely — tips" row inside the unlocked "Private details" card, right below the exact address/open-in-Maps button (visible to the host and to approved joiners, i.e. exactly whoever can actually see the real meeting point).
  - `app/chat/[id].tsx` — a dismissible-per-visit banner pinned above the message list ("Meeting up? Keep it public and don't share personal info here — tap for tips"), shown whenever the current user can chat (host or approved joiner). Dismissing it only hides it for that screen visit (local component state, not persisted) — it reappears next time chat is opened, matching how dating/marketplace apps keep this reminder live rather than letting it be dismissed forever.
